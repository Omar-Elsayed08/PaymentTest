# Everything Burger

Static shop site with a Stripe Checkout backend. Runs locally on Node, deploys
free to Cloudflare Workers.

## Why there is a backend at all

Everything in `shop/js/` runs in the shopper's browser and can be edited with
devtools, so prices can never be trusted from there. The cart only ever sends
product ids, sizes, colors, materials, and quantities. Prices are looked up
server-side in `backend/shared/catalog.js`, which is also the only place the
Stripe secret key exists.

## How variant pricing stays honest

A shirt's price depends on its material (essential cotton is $6 less than
oversized snow washed) and can be nudged by its colorway. Those rules live in
`shop/js/shop-data.js` for the product page.

Rather than restating them, `npm run build` runs that same file and writes every
buyable color/material pair, with its final price, into
`backend/shared/catalog-data.js`. One set of rules feeds both sides, so the
amount Stripe charges cannot drift from the amount on the page.

The same build also drops pairs that are not for sale. A colorway that only
lists snow washed renders does not exist in essential cotton, so asking for that
combination at checkout is refused instead of being priced from a fallback.

## Layout

Everything the browser downloads lives at the top level. Everything that
touches Stripe lives under `backend/` and is never served to visitors.

| Path | Purpose |
|---|---|
| `index.html`, `shop/`, `gallery/`, `about/`, `assets/` | the public site |
| `shop/shirts/shirts-data.js`, `shop/prints/prints-data.js`, `shop/more/more-data.js` | product definitions, the only place to edit products |
| `shop/js/shop-data.js` | variant rules: which pairs exist and what they cost |
| `shop/js/stripe-checkout.js` | posts the cart to the API and redirects to Stripe |
| `shop/js/checkout-config.js` | where the API lives, since Pages and the API are on different hosts |
| `backend/shared/` | checkout logic used by both runtimes |
| `backend/worker/index.js` | Cloudflare entry point (production) |
| `backend/server/` | Express entry point (local development) |
| `backend/scripts/` | build and verification steps |
| `wrangler.toml` | Cloudflare deployment config |

`backend/shared/catalog-data.js` and `dist/` are generated by `npm run build`.
Don't edit them by hand.

## Local development

```bash
npm install
cp .env.example .env      # then fill in your Stripe test keys
npm start
```

Open http://localhost:3000. Opening the HTML files directly will not work,
because checkout needs the API on the same origin.

To test webhooks, in a second terminal:

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

Copy the `whsec_…` it prints into `STRIPE_WEBHOOK_SECRET` and restart the
server. Pay with test card `4242 4242 4242 4242`, any future expiry, any CVC.
Paid orders append to `backend/server/var/orders.jsonl`.

To run the Cloudflare version locally instead:

```bash
cp .env .dev.vars         # wrangler reads secrets from .dev.vars
npm run cf:dev            # http://localhost:8787
```

Set `PUBLIC_BASE_URL=http://localhost:8787` inside `.dev.vars`.

To check pricing and validation without starting anything:

```bash
npm run verify
```

## Deploying

This repo is set up for the split arrangement: GitHub Pages keeps serving the
site, and Cloudflare runs only `/api/`. Pages serves static files and cannot
create a Stripe Checkout Session, because that has to be signed with the secret
key, which can never be sent to a browser.

The pieces are already configured:

| Setting | Where | Value |
|---|---|---|
| `ALLOWED_ORIGINS` | `wrangler.toml` | `https://everythingburger.studio` |
| `PUBLIC_BASE_URL` | `wrangler.toml` | `https://everythingburger.studio` |
| `WORKER_ORIGIN` | `shop/js/checkout-config.js` | the Worker's URL |

`shop/js/checkout-config.js` is the only place the API's location is written
down. It points the browser at the Worker on the live domain and leaves it alone
on `localhost` and `*.workers.dev`, where the API is already same-origin, so
`npm start` keeps working untouched.

To deploy:

```bash
npx wrangler login
npx wrangler secret put STRIPE_SECRET_KEY
npx wrangler secret put STRIPE_WEBHOOK_SECRET
npm run cf:deploy
```

Cloudflare prints the Worker's URL. Confirm it matches `WORKER_ORIGIN` in
`shop/js/checkout-config.js`, then push so Pages picks up the site.

The Worker is not deployed by pushing to GitHub. Since the product catalog is
compiled into it, **run `npm run cf:deploy` whenever you edit a product file**,
or the site will show a new price while the Worker still charges the old one.
Connecting the repo in Cloudflare's dashboard, or adding a workflow that uses
`cloudflare/wrangler-action`, removes that footgun.

`_config.yml` keeps `backend/`, `wrangler.toml`, and `package.json` out of the
published Pages site. No secrets are in them, but there is no reason to serve
server code.

### The other option: move everything to Cloudflare

If the split ever feels like too many moving parts, the Worker can serve the
pages too. Add `everythingburger.studio` as a custom domain on the Worker in the
Cloudflare dashboard, turn off GitHub Pages for the domain so DNS points at one
place, and clear `ALLOWED_ORIGINS`. Then one deploy ships the site and the API
together and they can never drift apart.

### Webhooks in production

In the Stripe Dashboard, go to Developers → Webhooks, add an endpoint at
`https://your-worker-url/api/webhooks/stripe`, subscribe it to
`checkout.session.completed`, reveal its signing secret, and store it with
`npx wrangler secret put STRIPE_WEBHOOK_SECRET`. This is a different value from
the one the Stripe CLI prints locally.

Redeploy any time with `npm run cf:deploy`. The build regenerates the catalog
from the product files, so adding a product is an edit plus a deploy.

## Going live

Test keys never move real money. When ready:

- Switch off test mode in Stripe and complete their account activation
- Replace the secret with the live key: `npx wrangler secret put STRIPE_SECRET_KEY`
- Create a live-mode webhook endpoint and store its signing secret the same way
- Confirm `PUBLIC_BASE_URL` matches your real domain over HTTPS

Stripe charges roughly 2.9% + 30¢ per card payment. Hosting stays free within
Cloudflare's 100,000 requests per day.

## Orders

On Cloudflare there is no writable disk, so paid orders are logged to
`wrangler tail` output rather than a file. The durable record is the Stripe
Dashboard, which stores every payment with the shipping address and a `cart`
metadata field describing what was bought, including the color and material of
each line. Enable Stripe's email notifications to get told about each sale.

## Configuration

Non-secret settings live in `[vars]` in `wrangler.toml` for production, and in
`.env` locally.

| Variable | Default | Meaning |
|---|---|---|
| `PUBLIC_BASE_URL` | — | origin used for Stripe redirects |
| `CURRENCY` | `usd` | Stripe currency code |
| `SHIPPING_CENTS` | `800` | flat shipping, `0` for free |
| `MAX_QTY_PER_LINE` | `20` | per-line quantity cap |
| `MAX_CART_LINES` | `30` | distinct items per order |
| `ALLOWED_SHIPPING_COUNTRIES` | `US,CA` | Stripe country allowlist |
| `ALLOWED_ORIGINS` | empty | hosts allowed to call the API from another origin |

`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are secrets. Locally they go in
`.env`; on Cloudflare they are set with `wrangler secret put`. `.env`,
`.dev.vars`, and `dist/` are gitignored and must stay that way.
